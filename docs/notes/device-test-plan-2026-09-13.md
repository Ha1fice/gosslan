## T1【最高优先】BLE 链路能不能活过 45 秒

**背景**：审计发现 BLE 读循环漏了回灌读活性 ⇒ 健康链路 15s 判不健康、45s 被看门狗拆掉。
本轮已修，需要你确认"真的不再自拆"。

**步骤**
1. 手机与 Mac 只开蓝牙（关 Wi-Fi），互相加好友、建立会话。
2. 保持两端都在前台，**什么都别做，静置 3 分钟**。
3. 第 2 分钟时，互相发一条消息。
4. 静置结束后，再互相发一条消息。

**期望**
- 3 分钟内**不应出现** `-conn peer=… 读活性超过 45s 无入站帧 ⇒ 拆除死链路`（这是"自拆"的标志）。
- 第 2 分钟那条消息应**立即送达**（不应等几十秒）。
- 链路徽标应一直显示"蓝牙直连"，不应时有时无。

**要贴给我**
- 两边日志里所有 `mesh` 与 `ble` 行（尤其 `[GATT]` / `-conn` / `[SEND]` / `[RECV]` / `[FRAG]`）。
- 如果第 2 分钟的消息延迟 > 2s，请贴时间戳。

## T2【最高优先】BLE 到底是什么速度（MTU 基准）

**背景**：文档里的"1KB/s、MTU=23"是**猜的**。本轮加了两条日志，可以一次测准。

**步骤**
1. 连上 BLE 后，在日志里搜 `[GATT] MTU 协商结果` 与 `[GATT] 外设侧 MTU 协商结果`。
2. 发一条**纯文字**消息（例如 10 个字），记录两端 `[SEND] … bytes=… 分片=n` 的 `bytes` 与 `分片`。
3. 发一张 **100~200KB 的图片**，秒表记「本机开始发送 → 对端看到图片」的墙钟时间。
4. 再发一张 **1MB 左右的大图**，同上（**很可能失败，见 T3，失败也是有效结论**）。

**期望 / 我要算的数**
- `每片有效载荷`（两条 MTU 日志）；
- 文字消息的 `分片数 ÷ 耗时` ⇒ 每片实际间隔；
- 图片的 `字节数 ÷ 耗时` ⇒ 真实 KB/s。

**要贴给我**
- 两条 MTU 日志原文；文字消息的 `[SEND]` 行；两次图片传输的起止时间与结果（成功/卡在"发送中"/报错文案）。

> 有了这三个数，我才能判断瓶颈是"MTU 没协商上"还是"每片 12ms 的节流"，
> 并据此决定要不要动 `NOTIFY_CHUNK_INTERVAL` 和主动 `requestMtu`。

## T3【高】大文件能不能传完（已知会失败，做基线）

**背景**：`file.rs` 固定 30s 等 `FileCompleteAck`，而 1MB 的块在 1s 内全入队 ⇒ 必然超时 ⇒
每 5s 从头重传，且 `seq` 从 0 重来 ⇒ 接收方报**「文件分片顺序错误」**。

**步骤**：BLE 直连下依次发 **50KB / 200KB / 1MB** 三个文件（图片或文档都行），每个等 3 分钟。

**期望（当前版本）**
- 50KB 可能能成；200KB 以上大概率卡"发送中"或对端报"文件分片顺序错误"。
- 请记录：卡住时的**具体提示文案** + 两端 `[SEND] type=file_chunk` / `[RECV] … 顺序错误` 的行。

**这条测完就能确认我给的修法（改成"进展驱动超时"）是否对准了靶子。**

## T4【高】手机 ↔ 电脑 mesh（BLE-only，关 Wi-Fi）

**步骤**：关掉两边 Wi-Fi → 只靠蓝牙 → 互发文字 / 图片 / 语音（若有）→ 断一次再连。

**要看**：`[GATT]` 握手是否一次成功；断链后**多久**重连上（记秒表）；重连期间发的消息是否最终到达。

## T5【高】手机 ↔ 手机（两台安卓，BLE-only）

**步骤**：两台安卓只开蓝牙 → 互相搜索 → 加好友 → 互发消息 → 各退到后台 1 分钟再回来 → 再互发。

**已知边界**（不是 bug，如实记录程度即可）：Android 后台扫描被系统限流，
Rust 侧后台节奏是 30s；被系统杀掉则不扫描。

**要看**：加好友能否成功；`[SCAN] 收到 N 个广播，其中 M 个是本应用服务` 的 M 是否 ≥1。

## T6【中】三节点中继（手机A → Mac → Windows/另一台手机）

**背景**：多跳"最窄路径"（3 节点、都同时在线、单聊、默认中继策略）代码上应能通，但**从未验收**。

**步骤**：A（手机，BLE）↔ B（Mac，BLE）↔ C（Windows 或第二台手机，LAN）。
A 与 C 不在彼此射程/网段内 → A 给 C 发消息。

**期望**：C 能收到（B 只做转发）。**群聊请单独记**（审计发现群消息在非成员中继处会被丢弃，很可能不通）。

**要贴给我**：B 的日志里有没有 `+conn`/转发相关行；A 上消息状态是否变成"已送达"。

**期望**：重连时间稳定且较短（当前没有"立刻重拨"，最快也要等下一轮扫描）。

## T9【Mac 专项】鼠标拖选文字选不中（用户 2026-09-13：Mac + **纯文字**也会）

已排除的两个原因（所以不用再怀疑它们）：
- **不是表情图片被拖走** —— 纯文字消息同样复现（用户已确认）。
- **不是内边距锚点** —— 气泡根已加 `select-text`（上一轮修复），仍是同样表现。

剩下的可能只剩两类：**① 全局层面的 WebView/系统行为；② 我们这个页面的 DOM 结构**。
下面两步能把范围**一刀切开**，请按顺序做。

### 第一步（不用重新打包，1 分钟）

在**同一个 app、同一台 Mac**上，分别尝试用鼠标拖选：

1. **运行日志**窗口里的一行日志；
2. **设置 → 关于**里的设备指纹；
3. 一条长文本消息 → 点「展开」→ 在**弹窗**里拖选那段文字；
4. （对照）聊天区气泡正文 —— 已知失败。

**判读**
- 若 1/2/3 **有一个能选中** ⇒ 问题只在我们**消息行**这块 DOM（我继续按 DOM 方向查，
  重点查虚拟列表的行容器与 `user-select` 继承）；
- 若 1/2/3 **全都选不中** ⇒ 是 **WKWebView / Tauri 全局**层面的问题（下一步）。

### 第二步（需要重新打包一次，验证一个具体假设）

最可疑的全局因素是 `src-tauri/tauri.conf.json` 里的 `"dragDropEnabled": true`
（wry 会把 WKWebView 注册成 `NSDraggingDestination`，可能与 WebKit 自己的选区拖拽打架）。

我已经准备好一份**只改这一个开关**的覆盖配置（没有改主配置，随时可丢）：

```bash
cd src-tauri
CARGO_HOME="$PWD/target/cargo-home" \
  npx tauri build --features bluetooth --target aarch64-apple-darwin --bundles app \
  --config tauri.nodrop.conf.json
bash ../scripts/pack-macos-app.sh aarch64-apple-darwin
```

装上这个包后再拖选一次：

- **能选中了** ⇒ 确认是 `dragDropEnabled` 的副作用。接下来是一个取舍：
  关掉它就**失去"把文件拖进聊天框发送"**（那是 Tauri 原生拖放提供的真实路径）。
  可以做的折中：默认关、在设置里给个开关；或保留原生拖放但另找选区方案。
- **还是选不中** ⇒ 那就是 macOS/WKWebView 层面的（已知 macOS 15 有一条选区回归），
  我会转去查系统版本 + wry 版本的已知问题，不再在 CSS/DOM 上耗。

> 把这两步的结果贴给我即可（第一步只要一句"1/2/3 哪个能选中"）。
